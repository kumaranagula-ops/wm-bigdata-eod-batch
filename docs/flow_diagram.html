Level 1

How the project is built and run

The order you run things in, from an empty machine to data in Snowflake.

  1. Generate the source data

    make data

    scripts/generate_data.py writes deterministic fake data: the MySQL CRM seed, NAS feeds for 3 business dates (trades, cash, corporate actions, custodian positions, _SUCCESS), vendor market data, and Kafka event files. Bad rows, corrections, cancels, a stock split and recon breaks are planted on purpose.

    → nas/inbound/<date>/ · data/market/ · data/kafka/ · sql/mysql/init/02_seed.sql

  2. Package the Spark code

    make build

    Zips the wm_pipeline package into dist/wm_pipeline.zip and copies the entry script jobs/run.py. spark-submit ships both to YARN with --py-files.

    → dist/ (bind-mounted into the Airflow container)

  3. Start the infrastructure

    make up

    Starts the aether stack (HDFS, YARN, Hive Metastore, HiveServer2, Spark, Airflow) with this project's override file, which mounts the DAG, package, config, NAS folder and .env into Airflow. Then starts wm-mysql (loads the seed on first start) and wm-kafka, creates the Kafka topic and the Airflow pool wm_yarn.

    → docker-compose.yml · docker-compose.airflow-override.yml · network aether-bigdata

  4. Simulate the source systems for the day

    make crm-changes make kafka-produce DATE=2026-11-09

    Applies day-2 CRM changes in MySQL (an advisor leaves, the book is reassigned, a new client opens an account) and publishes the day's intraday OMS trade events to Kafka, keyed by account.

  5. Trigger the batch for a business date

    make trigger DATE=2026-11-09

    Unpauses wm_eod_batch and starts a run with {"business_date": "2026-11-09"}. On schedule it runs Mon–Fri 22:00 UTC with {{ ds }}.

  6. Airflow runs each step as a Spark job on YARN

    Sensor → land files in HDFS → bronze (4 sources) → silver → gold → HiveQL reports + reconciliation → Snowflake. See Levels 2–5.

  7. Check the results

    scripts/dag_status.sh make status make yarn-logs JOB=… make beeline

    Task states, the run_control table and failed DQ checks, the driver log of any job, and SQL on the Hive tables.

  8. Serve from Snowflake

    make snowflake-setup

    Creates WM_DB.GOLD once. With WM_SNOWFLAKE_ENABLED=true every run publishes the gold marts, and you query them in Snowsight.

Step 5 · Gold

Exact dependencies: the sensor gates landing; bronze_nas_files and bronze_market need landing + catalog; bronze_crm_jdbc and bronze_trades_stream need only the catalog; silver_reference needs CRM + market; silver_transactions needs silver_reference + NAS files + stream. Every Spark task uses pool wm_yarn (1 slot), so YARN runs one Spark app at a time on its 4 GB node, while the graph still shows which steps are independent.

Level 3

Main blocks of airflow/dags/wm_eod_batch_dag.py

Top to bottom, in the order they appear in the file.

block 1

Imports and constants

Paths inside the container (NAS, market, dist/, pipeline.json), the WebHDFS URL, the Maven PACKAGES per connector (mysql, kafka, s3, snowflake), pool name, and the BUSINESS_DATE template: dag_run.conf.business_date or ds.

block 2

aws_env()

Reads the default profile from the mounted ~/.aws/credentials, only when the market source is S3.

block 3

spark_submit()

  • builds spark-submit --master yarn --deploy-mode cluster
  • adds memory, --py-files zip, --files config/key
  • adds --packages and extra --conf
  • passes secrets as ${VAR} env to driver + executors
  • streams output to the task log, fails on non-zero exit
block 4

webhdfs() · put_file()

Two-step WebHDFS upload: the NameNode answers 307 with a DataNode URL, then the file body goes there.

block 5

default_args and @dag(...)

Owner, 1 retry after 2 min, 30 min task timeout. Schedule 0 22 * * 1-5, no catchup, one active run, paused on creation, 3 h run timeout.

block 6

wait_for_nas_feed

PythonSensor in reschedule mode: checks for _SUCCESS every 60 s for up to 2 h, freeing the worker slot between checks.

block 7

land_to_hdfs task

Uploads every NAS file for the date to /data/wm/landing/nas/<date>/. In hdfs market mode it also lands the vendor files.

block 8

spark_task() factory

Turns a job name into a TaskFlow task in pool wm_yarn that calls spark_submit(job, business_date). Used for 8 of the tasks.

block 9

Tasks with special inputs

  • bronze_crm_jdbc: MySQL user/password env + JDBC driver
  • bronze_market: S3 keys, region endpoint, hadoop-aws
  • publish_snowflake: skips unless enabled; ships the private key file

Dependency wiring

Level 4

What happens when one task runs

Example: silver_transactions for 2026-11-09. Every Spark task follows the same path.

Airflow scheduler
Pool slot free → runs the task, which calls spark_submit("silver_transactions", "2026-11-09").
spark-submit client
Uploads run.py, wm_pipeline.zip, pipeline.json and any packages to HDFS staging, then asks YARN for an application.
YARN ResourceManager
Starts the ApplicationMaster container on the NodeManager. In cluster mode the Spark driver runs inside it, then executors get their own containers.
jobs/run.py
Parses --job --business-date --option, then importlib loads wm_pipeline.jobs.silver_transactions and calls run(args).
make_context()
load_config() reads pipeline.json; build_spark() creates the SparkSession with Hive support, UTC time zone, AQE, dynamic partition overwrite, corrected date parsing.
with ctx.audit():
The job body runs: read tables → transform (wm_pipeline/transforms) → write with insert_overwrite() or Iceberg MERGE → DQ checks.
Audit on exit
Writes one row to wm_audit.run_control (SUCCESS or FAILED, row counts, metrics). DQ results go to wm_audit.dq_results; a CRITICAL failure raises.
Back in Airflow
spark-submit exits 0 or non-zero → task success, or retry once after 2 min.
Level 5

Main blocks of each job script

Files under wm_pipeline/jobs/, in DAG order. Each runs inside with ctx.audit():.

setup_catalog.py

reads
resources/hive/01_bronze.hql, 02_gold_audit.hql, iceberg/01_silver.sql
writes
Hive Metastore definitions
  1. Load each SQL file from inside the zip
  2. Split into statements, run each with spark.sql
  3. All IF NOT EXISTS, so it is safe every run

bronze_nas_files.py

reads
HDFS /data/wm/landing/nas/<date>/
writes
wm_bronze.trades_raw, cash_activity_raw, custodian_positions_raw, corporate_actions_raw
  1. csv() helper: explicit schema, PERMISSIVE, _corrupt_record
  2. Four feeds: trades CSV, cash | file with MM/dd/yyyy, custodian CSV, corporate actions JSON
  3. Add audit columns: source file, load time, batch id
  4. Overwrite the business_date partition; count rows and malformed rows

bronze_crm_jdbc.py

reads
MySQL wm_crm: branch, financial_advisor, party, account
writes
wm_bronze.crm_*_raw, lake.wm_audit.jdbc_watermark
  1. Per table: previous high watermark − 60 min overlap
  2. Min/max id query for the bounds
  3. Parallel JDBC read: partitionColumn, 4 partitions, fetchsize
  4. Overwrite the extract_date partition
  5. MERGE the new watermark only after the write

bronze_market.py

reads
s3a://bucket/wm/market/ or HDFS landing/market
writes
wm_bronze.security_master_raw, prices_raw
  1. market_base() picks S3 or HDFS from WM_MARKET_SOURCE
  2. Security master CSV with a schema
  3. Prices JSON, price_date= partitions, last 10 days
  4. Warn if today's prices are missing

bronze_trades_stream.py

reads
Kafka topic wm.intraday.trades
writes
wm_bronze.trades_stream_raw, HDFS checkpoint
  1. readStream from Kafka, earliest, max offsets per trigger
  2. from_json on the value, keep partition/offset
  3. foreachBatch appends each micro-batch to Hive
  4. trigger(availableNow=True): catch up, then stop

silver_reference.py

reads
bronze CRM, security master, prices
writes
lake.wm_silver.dim_branch, dim_financial_advisor, dim_party, dim_account, dim_security, fact_price
  1. Latest row per key (overlap window can repeat keys)
  2. SCD1 MERGE on row-hash change; party e-mail masked
  3. SCD2 accounts: hash, effective_from, stage_scd2(), one MERGE closes + inserts
  4. Prices MERGE on (security, date)
  5. DQ: one current row per account, FA exists, unique CUSIP

silver_transactions.py

reads
bronze trades file + stream, cash, corporate actions; silver dims
writes
fact_trade, fact_cash_activity, ref_corporate_action, quarantine
  1. Union file + stream by name, drop exact duplicates
  2. validate_trades(): malformed, missing keys, orphan account, unknown security
  3. latest_trade_versions(): highest version, file beats stream
  4. MERGE trades; cash and corporate actions (flatten nested terms)
  5. Quarantine with reasons; row-count reconciliation; DQ

gold_book_of_record.py

reads
silver facts and dims, as of the business date
writes
wm_gold.tax_lots_open, positions_daily, realized_gains, cash_balances_daily, account_valuation_daily
  1. Accounts valid on the date (SCD2 as-of join)
  2. split_adjust() trades, then lot_ledger() running-quantity axes
  3. Latest close with max_by, broadcast
  4. Open FIFO lots → positions → realized YTD with short/long term
  5. Cash on trade-date and settle-date basis (running sum)
  6. Account valuation with asset-class pivot and estimated tax; DQ

gold_reporting.py

reads
wm_gold.account_valuation_daily
writes
wm_gold.advisor_book_daily, client_portfolio_summary
  1. SET hivevar:as_of_date
  2. Run resources/hive/gold_reporting.hql (also runs in beeline)
  3. Advisor book: FA, branch, region, firm levels with DENSE_RANK
  4. Client summary: allocation %, segment, NTILE decile

middle_office_recon.py

reads
gold positions, bronze custodian positions
writes
wm_audit.recon_breaks, dq_results
  1. Map both sides to account number + CUSIP
  2. Full outer join, classify: QTY_MISMATCH, MISSING_AT_CUSTODIAN, MISSING_IN_BOOKS
  3. Fill internal ids for ops; fail only on an abnormal break rate

publish_snowflake.py

reads
5 gold tables for the date
writes
WM_DB.GOLD.* in Snowflake
  1. Key-pair options from env + shipped key file
  2. Per table: DELETE the date as a preaction, then append
  3. Snowflake connector stages and runs COPY INTO
